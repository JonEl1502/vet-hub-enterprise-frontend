## 1. 🐞 Cannot add a billable item while EDITING an existing care-log entry

> *"The 66 KES beef carrots is for last fed pm. Can try to add, but nothing added.
> Ooh this happens on edit — so ensure it can add a billable item."*

- Reproduce: open a saved entry's ✎ (e.g. the 07:11 PM "Fed PM"), search an item in
  **Items used this day**, pick it → nothing is added.
- The search itself works: typing `Carr` returns *Beef & Carrot Stew (Dog) Portion ·
  KES 220 · 132.4 Portions in stock*. It is the ADD that does nothing.
- Adding from a **new** entry works, so the difference is the edit path.
- Where: `components/clinic/boarding/BoardingStayPage.tsx` — `dayEditor(dateKey)` is
  rendered twice, once per saved entry as `dayEditor(\`${k}#${l.id}\`)` and once for
  the day as `dayEditor(k)`. The `ConsumablePicker` inside receives
  `dayKey={dateKey}` — which in the per-entry case is `"2026-08-14#123"`, **not a
  day key**. Strong suspicion: that composite string is the bug — it will not match
  `localDay(c.createdAt)` and may break the add/list path. Check before assuming.

## 2. 🐞 An item added in the day editor is invisible until the entry is saved

> *"I also can't see the item I have added till I save entry — so fix that too."*

- ⚠️ **Possible regression from 2026-08-19.** `ConsumablePicker` gained
  `hideLoggedList` so the boarding day block would not print the same rows twice.
  The day block renders `consRowsFor(...)` from `dayCons` (server state, refreshed by
  `load()`), so a freshly added item *should* appear above the editor — verify that
  it does while the editor is open, and if not, either re-show the list inside the
  editor for unsaved entries or make the day block refresh cover it.
- Related files: `components/clinic/shared/ConsumablePicker.tsx` (`hideLoggedList`),
  `BoardingStayPage.tsx` (`consRowsFor`, `dayCons`, `load()`).

## 6. Grooming spawned from boarding must be linked both ways

> *"Let the grooming spawn from here and be linked to this day too, so that we know
> when it was added, be able to navigate to it and back. In grooming we can show
> where the grooming services were spawned from."*

- Grooming started from a boarding stay should record **which stay and which day** it
  came from, and be navigable **both directions**.
- The grooming record should display its **origin**, as a named source:
  `from direct visit`, `vet visit`, `vaccination`, `boarding`, `inpatient`, …
- This needs a stored origin (source kind + source id + day), so it is the one item in
  this batch that likely touches the **backend**. Scope it before building.

## 7. New Visit — patient picker

- Show **pet name, gender, breed, species** (today the tiles are avatar-only).
- Move the **Add patient** button **below** the horizontal patient list, not inline at
  its end.

## 8. Gate Check — too many nested cards

> *"I feel these are too many cards in cards."*

`GATE CHECK` → `BOARDING ASSESSMENT` → `ADMISSION GATE` is three nested bordered
cards before the first field. Flatten. Precedent: `ConsumablePicker`'s `flat` prop,
added for exactly this complaint on 2026-08-05.

## 9. Grooming — where checkout goes

> *"So I can checkout and go back to boarding/inpatient or go to billing tab."*

After a grooming **Checkout**, offer a route back to the **originating** boarding or
inpatient record, or straight to the **billing** tab. Depends on item 6 supplying the
origin link.
